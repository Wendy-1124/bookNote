# 分布式机器学习

这章可以用一条因果链串起来：

> 机器学习训练需要反复迭代 → 数据和模型越来越大 → 单机遇到内存墙、计算墙 → 上分布式 → 分布式又引入通信墙 → 于是需要并行策略、通信拓扑、一致性协议和更高层的编程接口。

后面的所有概念，其实都在回答同一个问题：**给定一个具体的机器学习任务，怎么切、怎么放、怎么同步，才能让模型训得成、训得快、训得稳？**

---

## 1. 起点：机器学习训练为什么天然适合分布式

机器学习训练本质上是在不断逼近一个更好的数学函数。一次训练迭代通常包含两个阶段：

1. **前向传播**：输入数据一层层往后算，得到预测结果。
2. **反向传播**：把预测结果和真实值比较，算出参数该往哪个方向调整，也就是梯度。

所以完整循环是：

```text
输入数据 → 前向传播 → 计算损失 → 反向传播 → 更新参数 → 下一轮迭代
```

这件事有几个天然特征：

| 特征 | 含义 | 对系统的影响 |
|------|------|-------------|
| 计算密集 | 大量矩阵乘法和向量运算 | 需要 GPU/加速卡 |
| 迭代性强 | 同一批逻辑要反复执行很多轮 | 每轮的计算和通信都会被放大 |
| 中间状态多 | 前向激活、梯度、优化器状态都要保存 | 显存压力大 |
| 可容忍小误差 | 训练过程有一定统计容错性 | 允许异步、压缩、近似等优化 |
| 参数收敛不均 | 有的参数快，有的慢 | 同步策略会影响收敛效率 |

这也是机器学习和 MapReduce 最大的不同：MapReduce 更像“一次性批处理”，而机器学习是“多轮反馈控制”。一旦数据和模型变大，每一轮的计算、存储、通信都会被反复放大。

---

## 2. 第一层矛盾：单机为什么扛不住

大数据时代的机器学习同时撞上三个增长：

1. **数据变大**：样本从百万级走向百亿级。
2. **模型变大**：参数从千万级走向千亿级甚至更高。
3. **时效要求变高**：业务希望更快训练、快速迭代，甚至实时更新。

这三个增长最后落到系统上，就是三堵墙。

| 问题 | 本质 | 直接后果 |
|------|------|----------|
| 内存墙 | 单卡显存放不下模型和训练状态 | 模型训不起来 |
| 计算墙 | 单卡算力不够，训练时间过长 | 模型训得太慢 |
| 通信墙 | 多机多卡之间频繁搬数据 | 加了机器也不一定快 |

这三堵墙不是并列静止的，而是前后相生的：

```text
数据变大 + 模型变大
        ↓
单机显存不够、算力不够
        ↓
必须拆到多机多卡
        ↓
多机多卡之间必须同步参数和梯度
        ↓
通信墙出现
```

所以分布式机器学习不是“为了炫技把程序拆开”，而是单机资源跟不上之后的必然结果。

---

## 3. 内存墙：为什么显存先爆

训练时的显存占用可以分成两类：

| 类型 | 内容 | 特点 |
|------|------|------|
| 静态内存 | 模型权重、梯度、优化器状态，例如 Adam 的一阶/二阶动量 | 训练过程中长期存在 |
| 动态内存 | 前向传播激活值、临时张量、算子 workspace | 随一次迭代上下波动 |

一次迭代内，显存峰值通常出现在前向传播结束时：

```text
显存占用
   ↑
   |         前向结束（峰值）
   |           /\
   |          /  \
   |         /    \     反向开始后逐层释放激活
   |        /      \        \
   |       /        \        \
   |      /          \        \____ 反向结束，只剩静态状态
   |_____/            \____________
   +--------------------------------→ 时间
     前向开始        反向开始     反向结束
```

这就解释了为什么很多内存优化都先从“削峰”入手：

- **Gradient Checkpointing**：少存一部分激活，反向时重新计算，用时间换显存。
- **混合精度训练**：用 FP16/BF16 降低权重、激活和梯度的存储成本。
- **参数/优化器状态切分**：例如 ZeRO，把模型状态拆到多卡。

如果削峰还不够，就必须进入更重的方案：**模型并行**或**流水线并行**。也就是说，模型并行不是一上来就用，而是内存墙逼出来的。

---

## 4. 计算墙：为什么只优化单机还不够

在单机上，常见优化包括：

| 手段 | 目的 |
|------|------|
| 数据加载优化 | 不让 GPU 等磁盘和 CPU |
| 算子优化 | 提高矩阵运算、访存和 kernel 调度效率 |
| 计算图优化 | 常量折叠、算子融合、死代码消除、表达式化简 |
| 混合精度 | 降低计算和访存成本 |

这些优化很重要，但它们只能提高“单卡速度”。当数据和模型继续变大时，单机优化会遇到天花板。

于是系统必须引入第二个杠杆：**增加加速卡数量**。

训练速度可以粗略看成：

```text
总训练速度 ∝ 单卡速度 × 加速卡数目 × 多卡训练加速比
```

单机优化主要提升第一个因子；分布式训练关注后两个因子：

| 杠杆 | 关注点 |
|------|--------|
| 加速卡数目 | 怎么把更多卡组织起来 |
| 多卡训练加速比 | 加了卡之后到底能快多少 |

理想情况下，加 N 张卡就快 N 倍。但现实中做不到，因为通信、负载不均和串行部分都会吃掉收益。

| 机器数 | 理想加速 | 可能的实际加速 |
|--------|----------|----------------|
| 1 | 1.0x | 1.0x |
| 4 | 4.0x | 3.5x |
| 8 | 8.0x | 6.2x |
| 16 | 16.0x | 11.0x |

这就引出下一个问题：**既然要上多机多卡，应该怎么切？**

---

## 5. 第二层方案：并行策略解决“怎么切”

神经网络可以抽象成一个有向无环图（DAG）：

- **工作量 W**：总计算节点数。
- **深度 D**：最长依赖路径。
- **平均并行度 W / D**：理论上值得使用的处理器数量。

如果有 p 个处理器，耗时大致是：

```text
Tp ≈ O(W/p + D)
       ↑      ↑
   计算分摊  依赖链带来的串行瓶颈
```

因此，并行训练的核心就是把“可并行的部分”拆出去，同时尽量减少拆分带来的通信。

### 5.1 数据并行：数据太多时，切数据

数据并行是最常见的方式：每张卡都有完整模型，但处理不同的数据分片。

```text
完整 batch
    ↓
切成多个数据分片
    ↓
每张 GPU 拿完整模型 + 一个数据分片
    ↓
各自计算本地梯度
    ↓
AllReduce 聚合平均梯度
    ↓
每张卡用同一个平均梯度更新模型
```

| 维度 | 数据并行 |
|------|----------|
| 解决的问题 | 数据太大、单卡算太慢 |
| 切什么 | 切数据，不切模型 |
| 每卡拥有 | 完整模型 + 数据分片 |
| 通信内容 | 梯度，大小约等于模型参数量 |
| 典型代表 | PyTorch DDP、Horovod |

数据并行的关键代价是：卡数越多，全局 batch size 越大，学习率和收敛策略也要跟着调整。这就是线性缩放法则、warmup 等训练技巧出现的原因。

### 5.2 模型并行：模型单层太大时，切层内参数

当单层参数矩阵太大，一张卡放不下或算不动，就要切模型。

```text
同一个 batch
    ↓
复制到多张卡
    ↓
每张卡保存同一层的一部分参数
    ↓
各自计算局部结果
    ↓
通信拼接，形成完整输出
```

| 维度 | 数据并行 | 模型并行（张量并行） |
|------|----------|----------------------|
| 主要目标 | 提升吞吐 | 解决单层模型太大 |
| 切分对象 | 输入样本 | 层内参数/张量 |
| 每卡数据 | 数据分片 | 完整或近似完整数据 |
| 每卡模型 | 完整模型 | 模型分片 |
| 通信时机 | 一轮迭代末尾同步梯度 | 每层计算中同步激活/局部结果 |

模型并行的通信更频繁，所以通常适合单机多卡内部使用，例如 NVLink 互联环境。跨机做张量并行的代价会很高。

### 5.3 流水线并行：模型层数太深时，切层间

如果模型很深，可以把不同层放到不同设备上，让数据像流水线一样经过各个阶段。

```text
GPU1: 层 1-4  →  GPU2: 层 5-8  →  GPU3: 层 9-12
     前向传激活值                         ↓
     反向传梯度 ←─────────────────────────
```

朴素流水线的问题是利用率低：

```text
时间 →
GPU1: [前向1-4] [空闲]    [空闲]    [反向]
GPU2: [空闲]    [前向5-8] [空闲]    [反向]
GPU3: [空闲]    [空闲]    [前向9-12] [反向]
```

所以实际会把一个 batch 再切成多个 micro-batch，让流水线尽快填满：

```text
时间 →
GPU1: [mb1前向] [mb2前向] [mb3前向] [mb4前向] ...
GPU2:          [mb1前向] [mb2前向] [mb3前向] ...
GPU3:                   [mb1前向] [mb2前向] ...
```

### 5.4 三种并行方式如何选择

| 模型/任务特征 | 优先考虑 |
|---------------|----------|
| 模型能放进单卡，但数据很多 | 数据并行 |
| 单层参数很大，单卡放不下 | 模型并行/张量并行 |
| 模型层数很深，总体放不下 | 流水线并行 |
| 超大模型训练 | 数据并行 + 张量并行 + 流水线并行的混合并行 |

一句话记忆：

- **数据并行**：多卡同模型，各算各的数据。
- **模型并行**：一层拆多卡，合起来才算完。
- **流水线并行**：不同层放不同卡，按阶段接力算。

## 6. 第三层问题：切开之后，参数放哪里

一旦进入数据并行，每个 worker 都会产生自己的本地梯度。系统必须回答三个问题：

```text
每个 worker 都有本地梯度
        ↓
需要得到全局平均梯度
        ↓
必须决定：
1. 参数放哪里？        → 参数分布/通信拓扑
2. 什么时候同步？      → 模型一致性
3. 怎么高效同步？      → 通信模式
```

先看“参数放哪里”。主流架构分成中心化和去中心化。

### 6.1 参数服务器：中心化方案

参数服务器（Parameter Server, PS）把参数和梯度聚合放在中心节点上。

```text
Worker1  Worker2  Worker3  Worker4
    \       |       |       /
   push    push    push    push
             ↓
        参数服务器
        聚合梯度、更新参数
             ↓
   pull    pull    pull    pull
    /       |       |       \
Worker1  Worker2  Worker3  Worker4
```

| 优点 | 缺点 |
|------|------|
| 实现简单，弹性好 | Server 容易成为瓶颈 |
| 天然支持异步 | Worker 多了以后要扩展和管理 Server |
| 容错可以通过 Server 冗余实现 | 中心节点压力大 |

PS 适合大规模异构集群，也适合早期推荐、稀疏参数、异步训练场景。

### 6.2 AllReduce：去中心化强一致方案

AllReduce 不设中心参数服务器，所有 worker 共同完成梯度聚合，并且每个 worker 最终拿到同一份全局梯度。

```text
GPU1 ─── GPU2
 │  \   / │
 │   \ /  │
GPU3 ─── GPU4
```

| 特点 | 说明 |
|------|------|
| 无中心瓶颈 | 通信压力分散到所有节点 |
| 强一致 | 每轮之后所有 worker 参数一致 |
| 适合同构高性能集群 | 例如多 GPU、多机高速网络 |
| 容错较弱 | 一个节点失败可能拖住整个同步过程 |

PyTorch DDP 的核心就是这一类思路，底层常通过 NCCL 等库完成集合通信。

### 6.3 Gossip：去中心化最终一致方案

Gossip 更激进：每个节点只和邻居交换参数或梯度，不追求每一轮都有全局一致模型。

```text
GPU1 ←→ GPU2
 ↕       ↕
GPU3 ←→ GPU4
```

| 特点 | 说明 |
|------|------|
| 无中心节点 | 没有单点瓶颈 |
| 最终一致 | 短期内各节点模型可能不同 |
| 容错较好 | 局部故障不一定拖垮全部 |
| 收敛依赖拓扑 | 网络连接越弱，收敛越难保证 |

三种参数分布方式可以这样对比：

| 维度 | 参数服务器 | AllReduce | Gossip |
|------|------------|-----------|--------|
| 中心节点 | 有 | 无 | 无 |
| 全局模型 | 有 | 有 | 无，最终一致 |
| 同步风格 | 同步/异步都可 | 同步为主 | 同步/异步都可 |
| 通信瓶颈 | Server 侧 | 无明显中心瓶颈 | 无明显中心瓶颈 |
| 典型场景 | 异构集群、稀疏参数 | 同构 GPU 集群 | 对强一致要求不高的训练 |

## 7. 第四层问题：参数什么时候同步

参数放在哪里解决的是拓扑问题；什么时候同步解决的是一致性问题。这里有三个典型协议。

### 7.1 BSP：完全同步，收敛稳但怕慢节点

BSP（Bulk Synchronous Parallel）要求所有 worker 都完成当前 step，才能统一更新。

```text
时间 →
Worker1: [计算] [等待] [计算]
Worker2: [计算] [等待] [计算]
Worker3: [计算很慢......] [计算]
                  ↑
             所有人等最慢节点
```

| 优点 | 缺点 |
|------|------|
| 数学上接近单机大 batch | 被 straggler 拖慢 |
| 收敛稳定 | 节点越多，等待越明显 |

### 7.2 ASP：完全异步，吞吐高但梯度会过期

ASP（Asynchronous Parallel）允许 worker 算完就更新，不等其他人。

```text
Worker1: [更新] [更新] [更新] [更新]
Worker2: [更新] [更新]
Worker3: [更新]
```

| 优点 | 缺点 |
|------|------|
| 等待少，硬件利用率高 | 梯度可能基于旧参数计算 |
| 吞吐高 | 收敛可能变慢甚至不稳定 |

### 7.3 SSP：限制落后程度，折中统计效率和硬件效率

SSP（Stale Synchronous Parallel）允许快节点领先，但最多领先 s 轮。

```text
s = 2

Worker1: [1] [2] [3] [等] [4] [5]
Worker2: [1] [2] [3]     [4] [5]
Worker3: [1] [2]             [3]
```

- s = 0：退化成 BSP。
- s = ∞：接近 ASP。
- s 是常数：在等待和过期梯度之间折中。

三者本质上是一条权衡线：

```text
等待越多 → 参数越一致 → 收敛越稳 → GPU 空闲越多

BSP ---------------------- SSP ---------------------- ASP
收敛最稳                  折中                    吞吐最高
```

| 协议 | 同步限制 | 收敛质量 | 训练速度 | 适用场景 |
|------|----------|----------|----------|----------|
| BSP | 必须等所有人 | 最高 | 最慢 | 小规模同构集群 |
| ASP | 不等任何人 | 最不稳定 | 最快 | 大规模异构集群、容忍陈旧梯度 |
| SSP | 最多差 s 轮 | 中等 | 中等 | 需要平衡速度和精度 |

## 8. 第五层问题：通信怎么变少、变快、变隐形

上面解决了“怎么切、参数放哪、什么时候同步”，但还没有解决最现实的问题：同步太贵。

深度学习通信有几个特点：

| 特点 | 原因 |
|------|------|
| 通信量大 | 梯度和参数通常是大矩阵 |
| 通信频繁 | 每轮迭代都要同步 |
| 突发性强 | 反向传播到某些层时梯度集中产生 |
| 和内存绑定 | 通信前后都要做数据搬运和缓冲 |

因此优化思路分两类。

### 8.1 让通信更快

- 使用高效通信库：NCCL、Gloo。
- 优化通信拓扑：Ring AllReduce、Tree AllReduce、Hierarchical AllReduce。
- 利用高速互联：NVLink、InfiniBand、RDMA。
- 合理划分节点组：机内通信和跨机通信分层处理。

### 8.2 让通信更少

- **梯度压缩**：只传重要梯度，或者低精度传输。
- **梯度稀疏化**：只同步 top-k 或超过阈值的梯度。
- **梯度融合**：把很多小梯度合并成大块，减少小包开销。
- **计算-通信重叠**：某一层梯度算出来就开始传，同时继续反向计算前面的层。

核心思想可以概括成一句话：**要么让路更快，要么少搬货，最好搬货的时候机器还在继续算。**

## 9. 把所有方案放进一个二维坐标

分布式训练方案可以用两个维度定位：

- **参数分布**：中心化 vs 去中心化。
- **模型一致性**：强一致 vs 弱一致/最终一致。

```text
                 中心化
                  ↑
      参数服务器    │    参数服务器
      + BSP/SSP   │    + ASP
      同步中心化    │    异步中心化
                  │
    ──────────────┼──────────────→ 模型一致性变弱
      强一致       │       弱一致/最终一致
                  │
      AllReduce   │    Gossip
      + BSP       │    去中心化异步
      同步去中心化  │
                  ↓
                去中心化
```

| 象限 | 架构 | 通信模式 | 典型代表 |
|------|------|----------|----------|
| 左上 | 中心化 + 强一致 | 参数服务器 + BSP/SSP | 同步 PS |
| 右上 | 中心化 + 弱一致 | 参数服务器 + ASP | DistBelief 异步 PS |
| 左下 | 去中心化 + 强一致 | AllReduce + BSP | PyTorch DDP |
| 右下 | 去中心化 + 弱一致 | Gossip + ASP | Gossip 训练 |

这张图的价值在于：它把各种系统名词变成了组合题。一个分布式训练系统，本质就是在“参数放哪”和“同步多严格”之间选一个位置。

## 10. 编程接口为什么越来越简单

早期分布式训练要求用户显式控制通信和设备放置；后来框架逐渐把这些细节藏起来。

| 阶段 | 写法 | 用户要关心什么 | 问题 |
|------|------|----------------|------|
| 原始 PS | push/pull/clock | 手动推梯度、拉参数 | 灵活但容易错 |
| TensorFlow 早期 | `tf.device` | 手动指定变量放在哪个设备 | 改代码多 |
| Horovod | 包装优化器 | 一行替换 optimizer | 主要适合数据并行 |
| TF Distribute | `strategy.scope()` | 声明分布式策略 | 更统一，但抽象更重 |

示例：参数服务器风格最原始的写法：

```python
grad = compute_gradient()
server.push(grad)       # 推梯度
params = server.pull()  # 拉参数
```

Horovod 把通信藏进优化器：

```python
opt = hvd.DistributedOptimizer(opt)
```

TensorFlow Distribute 把策略藏进作用域：

```python
strategy = tf.distribute.MirroredStrategy()
with strategy.scope():
    model = create_model()
```

接口演进的方向很清楚：**分布式细节越来越从业务代码里消失，用户从“手写通信”变成“声明策略”。**

## 11. PyTorch 分布式：底层通信、数据并行和通用 RPC

PyTorch 的分布式能力也沿着这条线演进：先支持多进程，再有底层通信，最后抽象出 DDP、RPC、弹性训练等能力。

| 阶段 | 能力 | 意义 |
|------|------|------|
| `torch.multiprocessing` | 单机多进程 | 为“一卡一进程”打基础 |
| THD | 早期分布式底层库 | 提供分布式通信基础 |
| `torch.distributed` | 多机张量交换 | 跨机训练成为可能 |
| C10D | 统一通信后端 | 成为 DDP 和 RPC 的基础 |
| RPC | 远程调用和分布式 autograd | 支持参数服务器、模型并行 |
| Elastic | 弹性训练 | 节点故障后可恢复 |
| Pipeline | 流水线并行 | 支持层间切分 |

核心组件可以分成三层：

```text
torch.distributed
        │
  ┌─────┼──────┐
  │     │      │
C10D   DDP    RPC
通信   数据并行  通用分布式执行
```

| 组件 | 作用 | 通信方式 | 典型用途 |
|------|------|----------|----------|
| C10D | 底层通信库 | 集合通信 + P2P | 一般用户不直接用 |
| DDP | 数据并行封装 | AllReduce | 最常见的多机多卡训练 |
| RPC | 通用分布式框架 | 点对点通信 | 参数服务器、模型并行、流水线并行 |

DDP 相比 `DataParallel` 的核心优势：

| 维度 | DataParallel | DistributedDataParallel |
|------|--------------|--------------------------|
| 进程模型 | 单进程多线程 | 多进程，通常每 GPU 一个进程 |
| 通信位置 | 主进程聚合，容易受 GIL 影响 | 各进程独立通信 |
| 梯度同步 | 集中式聚合 | AllReduce |
| 扩展性 | 主要单机多卡 | 单机多卡和多机多卡 |
| 计算通信重叠 | 较弱 | 更好 |

所以实践里，**数据并行优先用 DDP**；只有遇到模型太大、结构复杂或需要跨节点远程执行时，才进一步使用 RPC、流水线并行或更复杂的混合并行框架。

## 12. 最终总结：这章的因果主线

可以把整章浓缩成一张链路图：

```text
机器学习训练 = 多轮前向/反向迭代
        ↓
数据变大、模型变大、时效要求变高
        ↓
单机遇到内存墙和计算墙
        ↓
必须上多机多卡
        ↓
需要决定怎么切：数据并行 / 模型并行 / 流水线并行
        ↓
切开以后要同步参数和梯度
        ↓
需要决定参数放哪：参数服务器 / AllReduce / Gossip
        ↓
需要决定什么时候同步：BSP / SSP / ASP
        ↓
同步又带来通信墙
        ↓
通过通信库、拓扑、压缩、融合、计算通信重叠来优化
        ↓
最终由框架封装成 DDP、RPC、strategy.scope 等接口
```

第一章回答的问题可以整理成这张表：

| 问题 | 答案 |
|------|------|
| 为什么要分布式？ | 数据、模型、时效要求超过单机能力 |
| 单机主要卡在哪里？ | 内存墙和计算墙 |
| 分布式又引入什么新问题？ | 通信墙和一致性问题 |
| 怎么切计算？ | 数据并行、模型并行、流水线并行 |
| 参数放在哪里？ | 参数服务器、AllReduce、Gossip |
| 参数什么时候同步？ | BSP、SSP、ASP |
| 怎么让通信不拖后腿？ | 高效通信库、拓扑优化、梯度压缩、梯度融合、计算通信重叠 |
| 框架如何降低使用门槛？ | 把通信和同步封装进优化器、策略作用域、DDP/RPC 等接口 |

一句话收束：**分布式机器学习不是单纯“加机器”，而是在内存、计算、通信、精度和容错之间做系统性权衡。**
