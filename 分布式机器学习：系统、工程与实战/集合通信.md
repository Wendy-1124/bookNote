# 集合通信

集合通信是分布式训练的通信基础。它回答的问题不是“模型怎么训练”，而是更底层的：**多张卡、多台机器之间，怎么高效交换张量？**

这篇笔记可以用一条因果链串起来：

> 数据并行会让每张卡产生一份本地梯度 → 训练需要全局平均梯度 → 不能让所有梯度都挤到参数服务器 → 需要 AllReduce → AllReduce 属于集合通信 → MPI 提供了语义，但 GPU 训练需要 NCCL 这样的高性能实现 → Ring AllReduce 用拓扑和分块把带宽利用率拉满。

换成问题链就是：

```text
为什么要通信？
  因为每张卡只看到了自己的数据分片。

为什么通信不能随便写 send/recv？
  因为多卡规模一大，手写点对点通信复杂且容易低效。

为什么 AllReduce 最关键？
  因为数据并行需要“所有人贡献梯度，所有人拿到全局梯度”。

为什么还要关心 MPI、NCCL、Ring？
  因为语义正确只是第一步，还要让大张量在真实 GPU 集群上跑得快。
```

---

## 1. 为什么分布式训练离不开通信

以数据并行为例，每张 GPU 都有一份完整模型，但吃不同的数据分片。

```text
完整 batch
    ↓
切成多个数据分片
    ↓
GPU0/GPU1/GPU2/... 各自前向和反向
    ↓
每张卡得到自己的本地梯度
    ↓
必须把所有本地梯度求平均
    ↓
每张卡用同一份全局梯度更新模型
```

如果没有最后的梯度同步，每张卡的模型参数会越走越不一样，训练就不再等价于一个统一模型。

所以数据并行真正的核心不是“每张卡各算各的”，而是：**各算各的之后，怎么把结果合成同一个全局结果。**

这就引出了集合通信。

## 2. 通信参与者：world size、rank 和 group

分布式系统里，通信对象不能直接用“第几张卡”这种模糊说法，而要有统一编号。

| 概念 | 含义 | 直觉 |
|------|------|------|
| world size | 参与通信的总进程数 | 这个群里一共有多少人 |
| rank | 当前进程在通信组里的编号，范围是 `0 ~ world_size - 1` | 你在群里的座位号 |
| group | 通信子组 | 从大群里拉一个小群 |

为什么需要 rank？因为真实机器地址可能是 IP、端口、网卡、GPU 编号的组合，直接管理很麻烦。rank 把这些细节抽象掉：用户只需要说“发给 rank 2”，底层通信库负责把 rank 映射到真实地址。

```text
用户视角：rank 0 → rank 2
底层映射：rank 2 = node-1:GPU0:port
```

group 的作用是缩小通信范围。例如混合并行里，张量并行组、流水线并行组、数据并行组可能不是同一批进程。

```python
# 默认在 world group（所有进程）上通信
dist.all_reduce(tensor, op=dist.ReduceOp.SUM)

# 只在部分进程上通信
group = dist.new_group([0, 1, 2])
dist.all_reduce(tensor, op=dist.ReduceOp.SUM, group=group)
```

## 3. 两种通信模式：点对点 vs 集合通信

分布式程序里的通信可以分成两类。

### 3.1 点对点通信：一对一

点对点通信就是一个发送方对应一个接收方。

```text
进程 A ──────→ 进程 B
发送            接收
```

PyTorch 示例：

```python
# 进程 0
tensor = torch.zeros(1) + 1
dist.send(tensor, dst=1)

# 进程 1
tensor = torch.zeros(1)
dist.recv(tensor, src=0)
# 此时 tensor = [1.0]
```

点对点通信的优点是灵活，缺点是规模一大就很难手写和调度。比如 1024 张卡两两通信，如果完全由用户自己管理 send/recv，代码会非常复杂，也很容易死锁。

PyTorch 里点对点通信有阻塞和非阻塞两类：

| 函数 | 行为 | 适用场景 |
|------|------|----------|
| `send()` / `recv()` | 阻塞，直到通信完成 | 简单、确定的通信流程 |
| `isend()` / `irecv()` | 非阻塞，立即返回 work 对象，可 `.wait()` | 需要计算和通信重叠 |

### 3.2 集合通信：一组进程按固定模式通信

集合通信不是“一对一”，而是一组进程共同完成一个通信动作。它把常见通信模式抽象成标准原语，用户只描述“我要做什么”，底层通信库决定“怎么传最快”。

```text
Broadcast              Gather               AllReduce
  A                      A                     A
 ↓↓↓                    ↑↑↑                   ↓↓↓
B C D                  B C D                 B C D
一发给多               多收给一              多收再全发
```

集合通信的特点：

- 通信参与者是一组进程，而不是两个进程。
- 通信模式固定，例如广播、收集、归约。
- 用户不用手写每一条 send/recv。
- 底层可以根据硬件拓扑做优化。

一句话：**点对点通信像打电话，集合通信像群聊；分布式训练最常用的是群聊。**

## 4. 集合通信原语：每个原语解决什么问题

集合通信原语可以从三个角度理解：谁发、谁收、结果放在哪里。

| 原语 | 发送方 | 接收方 | 做什么 | 典型用途 |
|------|--------|--------|--------|----------|
| Broadcast | 1 个 | 所有 | 一份数据发给所有人 | rank 0 分发初始参数 |
| Scatter | 1 个 | 所有 | 一份数据切块，每人一块 | 数据分片下发 |
| Gather | 所有 | 1 个 | 每人一块，收拢到一个进程 | 汇总日志、结果收集 |
| All-Gather | 所有 | 所有 | 每人一块，所有人拿到全集 | 拼接分片张量 |
| Reduce | 所有 | 1 个 | 所有人数据做求和/最大等归约，结果给一个进程 | 汇总统计量 |
| All-Reduce | 所有 | 所有 | Reduce 后把结果给所有人 | DDP 梯度同步 |
| Reduce-Scatter | 所有 | 所有 | 先归约，再把结果分片给每人 | ZeRO、Ring AllReduce 第一阶段 |
| All-to-All | 所有 | 所有 | 每个人给每个人发不同数据 | MoE、复杂重分布 |
| Barrier | 所有 | 所有 | 同步屏障，所有人到齐再继续 | 调试、阶段同步 |

图解：

```text
假设有 3 个 rank：rank0、rank1、rank2。

1. Broadcast：一个 rank 发，所有 rank 收到同一份数据

输入：
rank0: [A]
rank1: [ ]
rank2: [ ]

输出：
rank0: [A]
rank1: [A]
rank2: [A]

2. Scatter：一个 rank 把大数据切成多块，按 rank 分给每个人

输入：
rank0: [A B C]
rank1: [     ]
rank2: [     ]

输出：
rank0: [A]
rank1: [B]
rank2: [C]

3. Gather：所有 rank 各出一块，收拢到一个 rank

输入：
rank0: [A]
rank1: [B]
rank2: [C]

输出：
rank0: [A B C]
rank1: [     ]
rank2: [     ]

4. All-Gather：所有 rank 各出一块，最后每个 rank 都拿到全集

输入：
rank0: [A]
rank1: [B]
rank2: [C]

输出：
rank0: [A B C]
rank1: [A B C]
rank2: [A B C]

5. Reduce：所有 rank 的数据做归约，结果只放到一个 rank

输入：
rank0: [A0 B0 C0]
rank1: [A1 B1 C1]
rank2: [A2 B2 C2]

输出：
rank0: [sumA sumB sumC]
rank1: [             ]
rank2: [             ]

其中：sumA = A0 + A1 + A2，sumB/sumC 同理。

6. All-Reduce：所有 rank 的数据做归约，结果发给所有 rank

输入：
rank0: [A0 B0 C0]
rank1: [A1 B1 C1]
rank2: [A2 B2 C2]

输出：
rank0: [sumA sumB sumC]
rank1: [sumA sumB sumC]
rank2: [sumA sumB sumC]

7. Reduce-Scatter：先按位置归约，再把归约结果分片给所有 rank

输入：
rank0: [A0 B0 C0]
rank1: [A1 B1 C1]
rank2: [A2 B2 C2]

先归约：
sumA = A0 + A1 + A2
sumB = B0 + B1 + B2
sumC = C0 + C1 + C2

输出：
rank0: [sumA]
rank1: [sumB]
rank2: [sumC]

8. All-to-All：每个 rank 给每个 rank 发一块不同数据

输入：
rank0: [A0→0  A0→1  A0→2]
rank1: [A1→0  A1→1  A1→2]
rank2: [A2→0  A2→1  A2→2]

输出：
rank0: [A0→0  A1→0  A2→0]
rank1: [A0→1  A1→1  A2→1]
rank2: [A0→2  A1→2  A2→2]

9. Barrier：所有 rank 到齐后才能继续

rank0: 到达 barrier ─┐
rank1: 到达 barrier ─┼─ 所有人到齐 → 一起继续
rank2: 到达 barrier ─┘
```

这里最重要的是 AllReduce，因为数据并行训练中，每张卡都有本地梯度，每张卡最后又都需要同一份全局梯度。

## 5. AllReduce：为什么它正好匹配数据并行

数据并行的梯度同步可以写成一个公式：

```text
global_grad = (grad_0 + grad_1 + ... + grad_n) / n
```

每张卡都需要这个 `global_grad`，所以通信语义正好是：

```text
所有人贡献数据 → 做归约 → 所有人得到结果
```

这就是 AllReduce。

```python
tensor = torch.tensor([rank], dtype=torch.float32)
dist.all_reduce(tensor, op=dist.ReduceOp.SUM)
# 完成后，每个 rank 的 tensor 都是所有 rank 值的和
```

AllReduce 的常见归约操作：

| 操作 | 含义 | 例子 |
|------|------|------|
| SUM | 求和 | 梯度求和 |
| AVG | 平均 | 部分框架直接平均梯度 |
| MAX | 最大值 | 统计最大指标 |
| MIN | 最小值 | 统计最小指标 |
| PRODUCT | 乘积 | 少见 |

AllReduce 和 rank 的关系也很关键：

| 类型 | 是否依赖 rank 顺序 | 原因 |
|------|-------------------|------|
| AllReduce | 不依赖 | 加法、最大值这类归约满足交换律和结合律 |
| Scatter / Gather / AllGather | 依赖 | 第几块数据对应哪个 rank、最终拼接顺序是什么，和 rank 顺序有关 |

所以 AllReduce 的结果不关心 rank 编号怎么分配；但 Scatter、Gather、AllGather 这类“按位置分块/拼接”的操作必须关心 rank 顺序。

容易混淆的是 AllGather：它确实会让每个 rank 都拿到全集，但这个全集不是无序集合，而是按 rank 顺序拼出来的结果。例如：

```text
输入：
rank0: [A]
rank1: [B]
rank2: [C]

AllGather 输出：
rank0: [A B C]
rank1: [A B C]
rank2: [A B C]
```

如果 rank 编号变了，比如原来的数据 B 现在来自 rank0，A 来自 rank1：

```text
输入：
rank0: [B]
rank1: [A]
rank2: [C]

AllGather 输出：
rank0: [B A C]
rank1: [B A C]
rank2: [B A C]
```

也就是说，AllGather 的“每个人都有完整数据”不受影响，但完整数据里的排列顺序受 rank 影响。

## 6. AllReduce 可以拆成 Reduce-Scatter + All-Gather

理解 Ring AllReduce 前，要先记住一个重要等价关系：

> AllReduce = Reduce-Scatter + All-Gather

也就是：

```text
第一步：Reduce-Scatter
所有人先参与求和，但每个人只保留一块求和结果

第二步：All-Gather
大家互相交换分片，最后每个人都拿到完整求和结果
```

示例：3 张卡，每张卡都有一份完整梯度，并且这份梯度被切成 A、B、C 三块。

```text
初始状态：每张 GPU 都有完整梯度，只是数值来自自己的本地数据

GPU0: [A0, B0, C0]
GPU1: [A1, B1, C1]
GPU2: [A2, B2, C2]

目标：每一块都要分别求和

sumA = A0 + A1 + A2
sumB = B0 + B1 + B2
sumC = C0 + C1 + C2

第一步：Reduce-Scatter

先完成求和，但不要让每张 GPU 都拿完整结果；
而是把求和结果“分散”保存，每张 GPU 只保留其中一块。

GPU0: [sumA,   -,    - ]   只拿到 A 块的求和结果
GPU1: [  -,  sumB,   - ]   只拿到 B 块的求和结果
GPU2: [  -,    -,  sumC]   只拿到 C 块的求和结果

第二步：All-Gather

每张 GPU 把自己手里的那块 sum 结果发给其他 GPU，
最后所有 GPU 都拼出完整结果。

GPU0: [sumA, sumB, sumC]
GPU1: [sumA, sumB, sumC]
GPU2: [sumA, sumB, sumC]
```

这个拆法的价值在于：每一步都只传一部分数据，而不是每次都传完整梯度。Ring AllReduce 正是利用这个性质来提高带宽利用率。

换句话说，AllReduce 的表面语义是“所有人拿完整结果”，但高性能实现通常不会傻傻地先把完整数据集中到某个地方再发出去，而是把它拆成两个更适合并行传输的阶段：

```text
Reduce-Scatter：边传边求和，先让每个人负责一块最终结果
All-Gather：再把每个人负责的那块结果传播给所有人
```

## 7. 从参数服务器到 MPI_AllReduce：为什么要去中心化

早期分布式训练常用参数服务器。它的结构很直观：Worker 把梯度推给 Server，Server 聚合后再把新参数发回 Worker。

```text
Worker1: 本地梯度     Worker2: 本地梯度
          \               /
        参数服务器（中心瓶颈）
          /               \
Worker1: 全局梯度     Worker2: 全局梯度
```

问题在于，Worker 越多，Server 越容易成为瓶颈。所有梯度都要经过中心节点，网络入口和出口都会被打满。

MPI_AllReduce 给了另一种思路：不设中心节点，让所有 Worker 共同完成归约。

```text
Worker1 ←─────────→ Worker2
    ↕                    ↕
Worker3 ←─────────→ Worker4

所有 Worker 直接协作通信，没有参数服务器中心瓶颈
```

这里的 MPI 指的是 **Message Passing Interface**，也就是“消息传递接口”。它不是某一种具体网络协议，而是一套并行计算通信标准，主要用在 HPC（高性能计算）里。

MPI 的核心思想很简单：

```text
一个并行程序启动多个进程
  ↓
每个进程有自己的编号 rank
  ↓
进程之间通过消息传递交换数据
  ↓
可以用点对点通信，也可以用集合通信
```

MPI 里几个概念和深度学习分布式训练几乎是一一对应的：

| MPI 概念 | 含义 | 深度学习里的直觉 |
|----------|------|------------------|
| process | 一个独立进程 | 一个 worker / 一个 GPU 进程 |
| communicator | 一组可互相通信的进程 | process group / 通信组 |
| rank | 进程在 communicator 里的编号 | rank0、rank1、rank2 |
| size | communicator 里的进程总数 | world size |
| point-to-point | 两个进程之间收发消息 | send / recv |
| collective | 一组进程共同通信 | broadcast、reduce、allreduce |

所以 `MPI_AllReduce` 可以理解成 MPI 标准里定义好的一个集合通信接口：所有进程都拿出一份本地数据，MPI 负责把它们归约，并把结果发回给所有进程。

```text
MPI_AllReduce(local_tensor, global_tensor, SUM)

每个进程输入：自己的 local_tensor
MPI 内部做：SUM 归约
每个进程输出：同一份 global_tensor
```

MPI_AllReduce 对机器学习特别合适，因为它的语义刚好匹配数据并行：

| 数据并行需求 | MPI_AllReduce 语义 |
|--------------|--------------------|
| 每个 Worker 有本地梯度 | 每个进程提供本地张量 |
| 需要全局求和/平均 | Reduce |
| 每个 Worker 都要拿到结果 | All |
| 每轮都重复执行 | MPI 进程长期驻留 |

这也是深度学习从 HPC 领域借用 AllReduce 思想的原因。

## 8. 为什么 MPI 语义对了，但 GPU 训练还需要 NCCL

MPI 解决的是“通信语义”问题：比如 AllReduce 应该让所有进程贡献数据、做一次归约、再让所有进程拿到结果。这个抽象本身非常适合数据并行。

但深度学习里的瓶颈不只在“语义对不对”，还在“数据到底怎么在硬件上搬”。GPU 训练时，梯度通常在 GPU 显存里，而不是 CPU 内存里。如果通信路径走得不好，数据可能会绕一大圈：

```text
不理想路径：
GPU 显存 → CPU 内存 → 网卡 → 对端 CPU 内存 → 对端 GPU 显存

更理想路径：
GPU 显存 → GPU 显存
或者：
GPU 显存 → 网卡 → 对端 GPU 显存
```

所以问题变成了：**同样是 AllReduce，怎么让 GPU 显存里的大张量沿着最快的硬件路径传输？** 这就是传统 MPI 不一定最擅长的地方。

| MPI 在 GPU 深度学习里的不足 | 更具体的原因 |
|-----------------------------|--------------|
| GPU 显存通信不一定最优 | 传统 MPI 主要从 CPU 进程通信发展而来，默认视角更偏主机内存和主机网络 |
| 拓扑感知不够精细 | 一台机器里可能有 NVLink、PCIe、NUMA、多个网卡；不同 GPU 到网卡的距离也不同 |
| 大张量要持续跑满带宽 | 深度学习每轮都同步大梯度，通信库必须稳定吃满 GPU 间链路和跨机链路 |
| 小张量也要降低延迟 | 反向传播会产生很多梯度张量，通信启动开销也会影响训练速度 |
| 容错模型不太适合长时间训练 | MPI 传统上更偏“进程组整体运行”，一个进程失败常常导致整个通信域失败 |

于是有了 NCCL。NCCL 的目标不是重新定义 AllReduce、Broadcast 这些语义，而是专门回答这个问题：**在 NVIDIA GPU 集群上，怎么把集合通信跑到尽可能快。**

NCCL 主要补了几块能力：

| NCCL 优化点 | 解决什么问题 |
|-------------|--------------|
| 拓扑感知 | 自动识别 GPU 之间是 NVLink、PCIe 还是跨机网络，尽量选择更快路径 |
| GPU Direct | 让 GPU 显存尽量直接和其他 GPU 或网卡通信，减少 CPU 中转 |
| 高带宽算法 | 使用 Ring、Tree、Hierarchical AllReduce 等算法，尽量跑满链路带宽 |
| 面向深度学习调优 | 针对“大张量、重复迭代、GPU 间通信”做优化 |
| 与框架集成 | PyTorch DDP 可以直接调用 NCCL 做梯度同步，用户不用手写通信细节 |

可以把 MPI、Gloo、NCCL 的分工理解成这样：

| 组件 | 主要定位 | 更适合的场景 |
|------|----------|--------------|
| MPI | 通用并行计算通信标准 | HPC、CPU 进程通信、传统超算任务 |
| Gloo | 通用集合通信库 | CPU 张量、调试环境、没有 NCCL 的场景 |
| NCCL | NVIDIA GPU 集合通信库 | 多 GPU、多机 GPU、PyTorch DDP 梯度同步 |

所以 PyTorch DDP 在 GPU 训练中通常优先用 NCCL：不是因为 MPI 的 AllReduce 语义错了，而是因为 NCCL 更懂 GPU 显存、GPU 拓扑和深度学习梯度同步的通信模式。如果是 CPU 训练、调试或没有 NVIDIA GPU 的环境，才更常见 Gloo。

## 9. Ring AllReduce：用环形拓扑跑满带宽

Ring AllReduce 的核心思想是：**把所有 GPU 排成一个逻辑环，每个 GPU 只和左右邻居通信。**

```text
GPU0 → GPU1 → GPU2 → GPU3
 ↑                    ↓
 └────────────────────┘
```

这样做有两个好处：

1. 没有中心节点，不会出现 Server 瓶颈。
2. 每条链路都可以同时工作，带宽利用率高。

Ring AllReduce 通常分两阶段。

### 9.1 阶段一：Reduce-Scatter

假设有 3 张 GPU，每张 GPU 的梯度都切成 3 块：A、B、C。

```text
初始状态：每张 GPU 都有完整梯度，但数值来自自己的本地 batch

          A 块   B 块   C 块
GPU0:    [A0    B0    C0]
GPU1:    [A1    B1    C1]
GPU2:    [A2    B2    C2]

Reduce 的目标：按列求和

A 块求和：sumA = A0 + A1 + A2
B 块求和：sumB = B0 + B1 + B2
C 块求和：sumC = C0 + C1 + C2

Scatter 的目标：不要让每张 GPU 都保存完整 [sumA sumB sumC]，
而是把求和结果分散保存到不同 GPU。

Reduce-Scatter 之后：

GPU0:    [sumA   -      - ]   负责保存 A 块求和结果
GPU1:    [ -    sumB    - ]   负责保存 B 块求和结果
GPU2:    [ -      -    sumC]  负责保存 C 块求和结果
```

这个过程不是一次完成的，而是沿着环分多轮传递。每一轮里，每张 GPU 同时做两件事：

1. 把自己当前负责传递的某一块数据发给环上的下一个 GPU。
2. 从环上的上一个 GPU 接收一块数据，并把它累加到自己本地对应的块上。

以 3 张 GPU 为例，逻辑环可以看成：

```text
GPU0 → GPU1 → GPU2
 ↑             ↓
 └─────────────┘
```

如果 GPU0 最终负责保存 A 块求和结果，那么 A 块会沿着环传到 GPU0，并在传递过程中不断累加：

```text
A0 在 GPU0
A1 在 GPU1
A2 在 GPU2

经过若干轮传递和累加后：
GPU0 拿到 sumA = A0 + A1 + A2
```

B 块和 C 块也在同一时间沿着环做类似的传递和累加，只是最终落到不同 GPU：

```text
GPU0 最终保存 sumA
GPU1 最终保存 sumB
GPU2 最终保存 sumC
```

因此经过 `N - 1` 轮后，每张 GPU 不会拿到完整 `[sumA, sumB, sumC]`，而是只拿到自己负责的那一块完整求和结果。这就是 `Reduce-Scatter` 里的 `Scatter`。

### 9.2 阶段二：All-Gather

Reduce-Scatter 结束后，求和已经完成了，但结果是“分散保存”的：每张 GPU 只拿到一块 `sum` 结果，还没有完整的全局梯度。

```text
All-Gather 开始前：

GPU0: [sumA   -      - ]   有 sumA，缺 sumB、sumC
GPU1: [ -    sumB    - ]   有 sumB，缺 sumA、sumC
GPU2: [ -      -    sumC]  有 sumC，缺 sumA、sumB
```

All-Gather 要做的事就是：**每张 GPU 把自己已有的那块 sum 结果发给其他 GPU，同时也从其他 GPU 收到缺失的 sum 块。**

```text
需要传播的内容：

GPU0 把 sumA 发给 GPU1、GPU2
GPU1 把 sumB 发给 GPU0、GPU2
GPU2 把 sumC 发给 GPU0、GPU1
```

在 Ring AllReduce 里，这个传播也不是一次广播完成，而是继续沿着环分多轮传递。每一轮里，每张 GPU 把自己已有的一块结果传给下一个邻居，同时从上一个邻居接收一块自己缺的结果。

经过 `N - 1` 轮后，每张 GPU 都收齐所有块：

```text
All-Gather 结束后：

GPU0: [sumA sumB sumC]
GPU1: [sumA sumB sumC]
GPU2: [sumA sumB sumC]
```

到这里，每张 GPU 都拿到了完整的全局梯度 `[sumA, sumB, sumC]`。如果训练需要平均梯度，再除以 GPU 数量 `N`，就可以用它更新自己的模型副本。

## 10. Ring AllReduce 为什么高效

Ring AllReduce 的关键不是“少通信”，而是“把通信均匀摊到所有链路上，并且每次只传一块”。

假设有 N 张卡，梯度大小为 M。

| 阶段 | 每轮传输 | 轮数 | 每卡总传输量 |
|------|----------|------|-------------|
| Reduce-Scatter | M / N | N - 1 | (N - 1)M / N |
| All-Gather | M / N | N - 1 | (N - 1)M / N |
| 总计 | M / N | 2(N - 1) | 2(N - 1)M / N |

当 N 很大时：

```text
2(N - 1)M / N ≈ 2M
```

也就是说，每张卡总共发送的数据量接近 2 倍模型大小，而不是随着 GPU 数量线性增长。

更准确地说，Ring AllReduce 的优势来自带宽利用：每个 step 所有链路都在同时传输，避免中心节点被打爆。

不过它也不是万能的：

| 场景 | Ring AllReduce 表现 |
|------|---------------------|
| 大张量、稠密梯度 | 很好，容易跑满带宽 |
| 小张量很多 | 延迟开销占比高，需要梯度融合 |
| 稀疏梯度 | 不一定划算，参数服务器可能更灵活 |
| 节点故障频繁 | 容错弱，一个节点失败会影响整个环 |
| 异构慢节点明显 | 慢链路会拖住整体 |

## 11. Ring AllReduce vs 参数服务器

两者不是谁完全替代谁，而是适合不同模型和集群。

| 维度 | Ring AllReduce | 参数服务器 |
|------|----------------|------------|
| 拓扑 | 去中心化，环状/分层 | 中心化 Server |
| 通信瓶颈 | 无中心瓶颈，但受最慢链路影响 | Server 侧容易成为瓶颈 |
| 参数形态 | 适合稠密参数 | 适合稀疏、高维、按 key 访问参数 |
| 容错 | 较弱 | Server 可冗余，容错更容易做 |
| 一致性 | 通常强同步 | 同步/异步都容易支持 |
| 典型场景 | CV、NLP、Transformer 数据并行 | 推荐系统、CTR、稀疏 embedding |

可以这样理解：

- 如果每一轮都要同步一整块稠密梯度，AllReduce/Ring 非常自然。
- 如果每个样本只访问少量稀疏参数，参数服务器更适合按 key 拉取和更新。

## 12. 实践中的几个注意点

### 12.1 集合通信调用必须所有成员一起参与

如果 group 里有 4 个进程调用 AllReduce，那 4 个进程都必须进入同一个通信调用。否则很容易卡死。

```text
rank0: all_reduce(tensor)
rank1: all_reduce(tensor)
rank2: 没有调用
rank3: all_reduce(tensor)

结果：rank0、rank1、rank3 可能一直等待 rank2
```

### 12.2 通信张量的 shape 和 dtype 要匹配

集合通信通常要求参与进程传入形状和类型兼容的张量。否则轻则报错，重则通信异常。

### 12.3 小张量要合并

大量小张量分别 AllReduce，会被启动开销和网络延迟拖慢。DDP 会把梯度按 bucket 合并，就是为了把小包变大包。

### 12.4 通信可以和计算重叠

数据并行里，每个 GPU 反向传播算出的是“本地梯度”。这些梯度最后必须 AllReduce，才能变成全局梯度。

如果不做重叠，流程会变成两个串行阶段：先把整个反向传播全部算完，再统一做梯度通信。

```text
不重叠：

时间向右 →

计算： [layer4反向][layer3反向][layer2反向][layer1反向]
通信：                                             [AllReduce 所有梯度]

总耗时 ≈ 反向计算时间 + 梯度通信时间
```

这种方式的问题是：计算阶段网络闲着，通信阶段 GPU 又在等网络。

反向传播本身是从后往前算的，所以靠近输出层的梯度会先产生，靠近输入层的梯度后产生。因此没必要等所有梯度都算完再通信：后面层的梯度一旦准备好，就可以先开始 AllReduce；与此同时，GPU 继续计算前面层的反向。

DDP 里通常不会每个小梯度都单独通信，而是把多个梯度合并成一个 bucket。某个 bucket 里的梯度都算完后，这个 bucket 就可以立刻开始异步 AllReduce。

```text
有重叠：

时间向右 →

计算： [layer4反向][layer3反向][layer2反向][layer1反向]
通信：              [bucket1 AllReduce]
                              [bucket2 AllReduce]
                                             [bucket3 AllReduce]
```

可以按这个顺序理解：

1. 反向传播先算完后面几层的梯度。
2. 这些梯度所在的 bucket ready 后，立刻启动 AllReduce。
3. GPU 不等待这个 bucket 通信结束，而是继续算前面层的梯度。
4. 后续 bucket ready 后也陆续开始通信。
5. 等反向传播结束时，很多通信已经在前面的计算过程中完成了。

所以通信和计算重叠的核心不是减少通信量，而是把一部分通信时间“藏”在反向计算时间里面。理想情况下，总耗时从：

```text
反向计算时间 + 梯度通信时间
```

变得更接近：

```text
max(反向计算时间, 梯度通信时间) + 少量收尾等待
```

实际效果取决于 bucket 大小、网络带宽、模型层计算量，以及通信能不能真正异步执行。

## 13. 最终总结：这章的因果主线

整章可以压缩成这条链：

```text
数据并行
  ↓
每张卡产生本地梯度
  ↓
每张卡都需要全局平均梯度
  ↓
需要 AllReduce
  ↓
AllReduce 是集合通信原语
  ↓
集合通信需要 world size、rank、group 来组织参与者
  ↓
MPI 提供了 AllReduce 的通用语义
  ↓
GPU 深度学习需要更懂硬件的 NCCL
  ↓
Ring AllReduce 通过 Reduce-Scatter + All-Gather 跑满带宽
```

核心结论：

| 问题 | 答案 |
|------|------|
| 为什么需要集合通信？ | 数据并行要同步多张卡的梯度 |
| 为什么 AllReduce 最重要？ | 它正好表达“所有人贡献，所有人得到结果” |
| 为什么不用纯参数服务器？ | 中心节点容易成为瓶颈 |
| 为什么 MPI 不够？ | 语义对，但不够懂 GPU 拓扑和显存通信 |
| 为什么 NCCL 快？ | 拓扑感知、GPU Direct、高带宽集合通信算法 |
| 为什么 Ring AllReduce 高效？ | 分块传输、邻居通信、所有链路同时工作 |
| Ring 的局限是什么？ | 小张量、稀疏梯度、故障和异构慢链路 |

一句话收束：**集合通信是分布式训练从“多卡各算各的”走向“多卡协同训练同一个模型”的关键桥梁。**
